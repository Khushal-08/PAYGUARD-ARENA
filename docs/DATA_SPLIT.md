# PAYGUARD ARENA — Target Definition and Data Split

Since the competition dataset is generated entirely by our synthetic simulation (per SPEC.md Section 3 and the rules), the dataset is naturally chronological and entity-rich. We must structure our target and splits to emulate a live transaction scoring environment and strictly prevent temporal and entity leakage.

## Target Definition
- **Target Label**: `is_fraud` (Derived internally from `Transaction.label` == "Fraud").
- **Target Interpretation**: A binary indicator of whether a given transaction was generated by an adversarial campaign (Attack 1, 2, or 3) versus the legitimate baseline simulation.
- **Leakage Prevention**: The `campaign_id`, `round_id`, and `User.is_synthetic` fields are meta-labels that perfectly correlate with the target. These columns MUST be explicitly dropped from the dataset before any feature engineering or model training occurs.

## Data Split Strategy
To emulate a realistic production environment, we use a strict **Chronological Split** based on `Transaction.timestamp`. 

- **Training Set (60%)**: Used for fitting baseline feature distributions (e.g., historical user spend) and training the XGBoost model.
- **Validation Set (20%)**: Used for hyperparameter tuning, early stopping, and threshold calibration.
- **Test Set (20%)**: Frozen before Round 1 starts. This set never receives generated data from any adversarial rounds. Used to report the final known/unseen detection metrics.

### Leakage Precautions Between Splits
1. **No Future Lookahead**: When calculating behavioral baselines (e.g., a user's average spend) for a transaction at time *T* in the Validation or Test sets, we may only use transactions where `timestamp < T`.
2. **Strict Time Boundaries**: The simulation clock must guarantee that the latest timestamp in the Training Set is strictly earlier than the earliest timestamp in the Validation Set, and so forth for Test.
3. **Entity Leakage**: Synthetic Identity attacks (Attack 1) create new users. If an attack user is created during the Training window, they might exist in the Validation window. This is realistic (fraudsters build history). However, we must ensure that any aggregate features computed for them strictly obey the time boundary.
4. **Frozen Validation Rule**: As mandated by SPEC v2 Section 9, the Validation and Test sets are "frozen" before Round 1. Adaptive attacks generated in subsequent rounds are ONLY evaluated against the current model and added to subsequent training windows, never contaminating the frozen benchmark sets.

## Handling Missing Values
- **Simulation Benefit**: Because we generate the data, structural missingness is known. For example, `campaign_id` is missing for all legitimate transactions (which is why it's dropped).
- **Feature Missingness**: If a user has no prior transactions, behavioral features (like `velocity_24h` or `avg_spend_30d`) will be explicitly filled with 0, as this accurately represents a new entity with no history.
